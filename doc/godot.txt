以下内容按 **Godot 4.7.2-stable**（当前最新稳定版）的真实仓库结构整理。结构信息来自 GitHub API 上该 tag 的实际目录树（顶层、`core/` 全部子目录、`servers/rendering`、`scene/main`、`editor/{gui,scene,docks,plugins}`、`modules/`、`platform/`、`drivers/`、`thirdparty/`、`main/` 等均已核对）。说明一点：仓库有上万文件，其中约一千是 `doc/classes/*.xml`、约两千是 `thirdparty/` 和 `modules/` 里的第三方源码，逐个文件写"作用"没有信息量；因此下面采用 **".h/.cpp 文件对为一个单位 + 目录级依赖说明 + 关键文件的逐文件说明"** 的方式，覆盖全部有架构意义的文件。

# 一、顶层：先看仓库骨架

```
godot/
├── SConstruct              主构建脚本（SCons 入口）
├── methods.py              构建公共函数库
├── platform_methods.py     平台相关构建函数
├── version.py              版本号定义（被 SConstruct 读入）
├── scu_builders.py         单编译单元（SCU）生成器
├── gles3_builders.py       GLES3 着色器 → C++ 头文件生成
├── glsl_builders.py        GLSL 源内嵌生成
├── pyproject.toml / .clang-* / .editorconfig / .pre-commit-config.yaml
├── AUTHORS.md DONORS.md CHANGELOG.md CONTRIBUTING.md COPYRIGHT.txt LICENSE.txt README.md
├── core/       引擎地基：数据类型、容器、对象模型、IO、OS 抽象
├── main/       程序入口与主循环（Main::setup / start）
├── servers/    低层服务抽象：渲染、物理、音频、导航、显示、XR、文本
├── scene/      场景图与游戏对象：Node、2D/3D 节点、GUI、资源类型、动画
├── editor/     编辑器（仅 tools=yes 时编译）
├── modules/    可选功能模块（GDScript、mono、gltf、各图片格式…）
├── platform/   平台移植层（windows/linuxbsd/macos/android/ios/web/visionos）
├── drivers/    图形与音频后端（vulkan/d3d12/metal/gles3/alsa/wasapi…）
├── thirdparty/ 第三方库源码（69 个库）
├── doc/        文档：classes/*.xml + 生成工具
├── tests/      doctest 单元测试
└── misc/       发行脚本、图标、错误抑制、CI 辅助
```

**编译/链接依赖是一条严格单向的链**，理解它比记文件名重要：

```
core          （不依赖任何上层；只用 C 运行时 + 少量 thirdparty 头）
  ↑
modules/*     （每个模块 config.py 声明 depends；多数只依赖 core，少数依赖 servers/scene/editor）
  ↑
servers/*     （依赖 core；渲染依赖 drivers 的 RenderingDevice 后端）
  ↑
scene/*       （依赖 core + servers）
  ↑
editor/*      （依赖 core + servers + scene + 各模块的 editor 插件部分）
  ↑
main/*        （依赖以上全部，负责组装与启动）
platform/*    （横切：实现 core/os、drivers 所需的平台原语，并被 main 调用）
```

运行时相反：`main` 调 `register_core_types()` → `register_server_types()` → `register_scene_types()` → `register_editor_types()`，把各层类注册进 `ClassDB`；每个目录的 `register_*_types.cpp` 就是这条注册链的节点。

# 二、构建系统：每个目录的 SCsub 才是"该目录的说明书"

| 文件 | 作用 | 依赖关系 |
|---|---|---|
| `SConstruct` | 总入口：解析 `platform=`/`target=`/`tools=` 等参数，检测编译器与架构，创建 `env`，按顺序 `SConscript` 各目录，最后链接出 `godot` 可执行文件 | 读 `version.py`、`methods.py`、`platform_methods.py`；生成 `modules/register_module_types.gen.cpp` |
| `methods.py` | 公共构建函数：`add_source_files`、模块探测（`detect_modules`）、警告开关、`split_lib`、第三方库编译辅助 | 被所有 `SCsub` 调用 |
| `platform_methods.py` | 架构/平台相关工具：`arch_from_bytes`、目标三元组、平台默认选项 | 被 `platform/*/detect.py` 与 `SConstruct` 使用 |
| `version.py` | 版本四元组与状态（stable/dev），并写入 `core/version.h` 的宏 | 被 `SConstruct`、`main`、`editor` 读取 |
| `scu_builders.py` | 把多个 `.cpp` 合并为单个翻译单元（unity build），加速增量编译 | 被 `methods.py` 调用 |
| `glsl_builders.py` | 把 GLSL 着色器源码转成 C++ 字节数组头文件 | 被 `servers/rendering/**/SCsub` 使用 |
| `gles3_builders.py` | GLES3 专用着色器变体生成 | 被 `drivers/gles3` 使用 |
| `*/SCsub`（每个目录一个） | 该目录"编译哪些文件、需要哪些宏、依赖哪些库"的唯一权威说明 | 由父目录 `SCsub` 递归进入 |
| `modules/*/config.py` | 模块元数据：`can_build`、`depends`、`module_deps`、`enabled` 逻辑 | 被 `methods.py` 与 `SConstruct` 解析 |
| `*/register_*_types.cpp` | 类型注册入口（core/server/scene/editor/platform/driver/module 各一份） | 向上依赖被注册类的头文件；被 `main` 调用 |

> 经验：想改某个功能，先看它所在目录的 `SCsub` 和 `config.py`，能立刻知道它的编译依赖与可选性。

# 三、`core/`：引擎地基（约 420 文件，全部列出）

`core` 只依赖 C 运行时与极少数 header-only 第三方库，是整个引擎的"标准库"。

## 3.1 `core/` 根

| 文件 | 作用 | 依赖 |
|---|---|---|
| `core_bind.cpp/.h`、`core_bind.compat.inc` | 把 core 层单例与静态工具类集中绑定到 `ClassDB`（供脚本/序列化使用），compat.inc 放兼容性别名 | → `class_db`、`object` |
| `core_constants.cpp/.h` | 注册全局常量枚举（按键、鼠标、MIDI、错误码、属性提示等） | → `core/input`、`core/error` |

# 十三、把依赖串起来：几条真实调用链

**1）画一个精灵**
`scene/2d/sprite_2d.cpp` → `CanvasItem::_draw` → `RenderingServer::canvas_item_add_texture_rect` → `RendererCanvasCull` → `RendererCanvasRenderRD` → `RenderingDevice` → `drivers/vulkan`（或 d3d12/metal）。

**2）输入**
`platform/windows/display_server_windows`（WndProc）→ `Input::parse_input_event` → `InputMap` 匹配动作 → `SceneTree::_call_input_pause` → `Node::_input/_unhandled_input` → `Control::gui_input`。

**3）物理**
`RigidBody3D`（scene/3d）→ `PhysicsServer3D`（servers/physics_3d）→ `godot_physics_3d` 或 `jolt_physics`（modules）→ `body/space/step` 求解 → 回调 `_integrate_forces`。

**4）资源加载**
`ResourceLoader::load("res://x.tscn")` → 按扩展名选 `ResourceFormatLoader`（`resource_format_binary` / `image_loader_png` / `gltf` 模块）→ `FileAccess` 后端（PCK/ZIP/磁盘/加密）→ `ResourceCache` 命中检查 → 实例化。

**5）脚本**
`.gd` 文件 → `GDScriptLanguage::load`（modules/gdscript）→ `GDScriptParser`→`Analyzer`→`Compiler`/`ByteCodeGen` → `GDScript` 资源 → `GDScriptInstance`（实现 `ScriptInstance`）挂到 `Object` → `GDScriptFunction::call` 在 VM 中执行。

**6）编辑器启动**
`main/main.cpp` → `EditorNode`（editor/editor_node）→ `EditorFileSystem` 扫描 → `EditorImportPlugin` 队列 → `EditorInspector`/`SceneTreeDock`/`EditorPlugin` 加载 → 运行游戏时 `EditorRun` 启动子进程或嵌入窗口。

# 十四、建议的阅读顺序

1. `core/object/object.h` → `class_db.h` → `variant/variant.h`（对象模型与反射，一切绑定与脚本的基础）
2. `core/templates/{cowdata,vector,hash_map,rid_owner}.h`（内存与容器约定）
3. `main/main.cpp` 的 `setup()/start()`（看清初始化顺序）
4. `servers/rendering/rendering_server.h` + `renderer_rd/renderer_scene_render_rd.cpp`（渲染主线）
5. `scene/main/node.h` → `scene_tree.h` → `viewport.h`（场景与主循环）
6. 挑一个具体功能纵向读：例如 `scene/2d/sprite_2d.*` → `RenderingServer` 对应方法 → RD 实现
7. 想看编辑器：`editor/editor_node.h` → `editor_data.h` → `editor/docks/*` → `editor/plugins/editor_plugin.h`
8. 想加功能：先看目标目录的 `SCsub`/`config.py`，再顺着 `register_*_types.cpp` 找注册点
